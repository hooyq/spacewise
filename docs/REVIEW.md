# 代码评审标准

人和 AI 评审 PR 时都按本文件执行。AI 评审只给意见，**合并必须由人批准**。

## 评审顺序

1. **正确性**：逻辑是否满足关联需求的验收标准？边界情况（时段跨天、并发抢同一座位、重复请求）？
2. **契约与边界**：是否违反 `AGENTS.md` 红线？跨模块接口变更是否同步更新了 spec 和调用方？
3. **数据**：迁移是否只新增？能否从空库重放？种子数据是否幂等？
4. **测试**：测试是否真的验证了行为？设想把实现改错，这些测试会不会失败？
5. **安全**：权限校验是否在服务端？是否有越权（学生 A 操作学生 B 的预约）？是否泄露个人信息？

## 严重程度

| 级别 | 含义 | 处理 |
|---|---|---|
| **Blocker** | 功能错误、数据损坏风险、安全漏洞、违反红线 | 必须修复才能合并 |
| **Important** | 缺少测试、契约不一致、明显的可维护性问题 | 原则上修复，或说明理由并记录 |
| **Nit** | 命名、风格等偏好 | 可忽略；每次评审最多提 3 条 |

## AI 生成代码的常见问题（重点检查）

- 测试“看起来完整但什么都没测”：断言常量、mock 掉被测方法、只覆盖成功路径
- 大段无关改动（顺手重构、改格式）
- 编造不存在的配置项、依赖版本或接口
- 吞掉异常、用宽泛的 `catch (Exception e)` 掩盖问题
- 时间与时区处理错误（本项目统一 Asia/Shanghai）
