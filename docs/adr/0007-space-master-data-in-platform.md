# ADR-0007：空间主数据（楼栋、教室、座位）由 platform-service 统一维护

- 状态：提议中（待组内确认）
- 日期：2026-10-21
- 决策人：（待填）
- 相关：ADR-0003；AGENTS.md 红线 2、跨模块写回

## 背景

M1（座位预约）、M2（整教室预约）、M3（报修）都要回答“在哪”：M1 预约的是座位，M2 预约的是教室，
M3 报修的位置可能是教室，也可能具体到某个座位。三个模块看到的必须是同一间教室、同一个座位，
否则跨模块写回（M3 维修中 → M1 下架该室座位；M2 审批通过 → M1 占用该室座位）无法对上号。

约束：每个服务只能连自己的库，服务间只能通过 HTTP 通信（红线 2）；不引入新的基础设施（红线 5）。
需要决定：楼栋、教室、座位这些“空间主数据”放在哪个服务，其他服务怎么引用。

现状：seat-service 的 `V1__create_room.sql` 建了一张 `room` 表，它只是分层示例，不代表归属已定。

## 候选方案

### 方案 A：放在 D（platform-service）
platform-service 维护楼栋、教室、座位，提供内部查询接口（含批量）和管理员维护接口；
M1/M2/M3 只保存 `room_id` / `seat_id`，各自保存自己的业务状态（预约、下架、占用、工单）。
- 优点：只有一份数据，不会出现不一致；三个模块地位对等，不互相依赖；与 AGENTS.md 中“公共层负责空间主数据”一致。
- 优点：M3 报修到座位级时，直接引用 D 的 `seat_id`，不用依赖 M1。
- 缺点：M1/M2/M3 展示教室名称、校验 ID 是否存在时都要调用 D，D 不可用时这些功能受影响。
- 缺点：跨服务没有外键，D 删除一间教室时，其他模块里的引用可能悬空。

### 方案 B：放在 M1（seat-service）
M1 维护教室和座位，M2/M3 调用 M1 查询。
- 优点：M1 用得最多，查询自己的库最快；现有 `room` 表可以直接沿用。
- 缺点：M2、M3 依赖 M1，而 M1 又要接收 M2、M3 的写回，形成双向依赖，M1 出问题会牵连所有模块。
- 缺点：“教室”对 M2、M3 同样重要，放在 M1 的组里维护，其他组改字段要跨组协调。

### 方案 C：各模块各存一份
每个模块自己建楼栋、教室表，靠约定的编号（如 `H3209`）对齐。
- 优点：各模块完全独立，不调用其他服务。
- 缺点：三份数据靠人手工保持一致，新增或改名教室要改三处；写回时用编号匹配，容易出错。
- 缺点：管理员要在三个地方维护同一份数据。

## 决定

选择**方案 A**：楼栋、教室、座位都由 platform-service 维护。

- 其他服务只保存 ID（`room_id`、`seat_id`），不复制名称等属性，需要时调用 D 的 `/internal/spaces/...` 查询。
- **业务状态不属于主数据**，留在各模块：座位“当前是否可约 / 下架 / 被占用”及其写入来源（M1/M2/M3）由 M1 记录；
  D 只回答“这个座位是否存在、属于哪间教室”。
- 管理员维护空间数据走 `/api/platform/spaces/...`。

## 依据

- 关键因素是**单一数据来源**：写回链路（M2/M3 → M1）全靠 ID 对齐，只有一份数据才可靠。
- 方案 B 的双向依赖会让 M1 成为单点；方案 C 的手工同步在学期项目里一定会出错。

## 代价与后续

- **依赖 D 的可用性**：提供批量查询接口，避免一次请求循环调用多次；D 不可用时调用方返回明确的错误，
  并且不影响调用方自己的 `/actuator/health`（AGENTS.md 已有约定）。暂不加缓存（红线 5）。
- **引用可能悬空**：在 `docs/specs/d-platform.md` 中约定删除规则（例如被引用的教室只能停用、不能物理删除）。
- **遗留示例表**：seat-service 的 `room` 表在实现 D 的空间接口时处理（新增 V2 迁移删除，或保留并注明仅为示例），
  具体写进那一步的计划；已合并的 V1 不修改。
- 字段、接口的细节写在 `docs/specs/d-platform.md`，不在本 ADR 里定。
- 如果后来发现 M1 调用 D 的次数多到影响性能，再重新审视（例如允许 M1 保存只读副本）。
