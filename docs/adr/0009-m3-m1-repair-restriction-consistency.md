# ADR-0009：M3 与 M1 采用持久化操作和幂等接口保证维修限制最终一致

- 状态：提议中（待 M1、M3 与项目负责人确认）
- 日期：2026-10-21
- 决策人：M3 起草；M1 与项目负责人待评审
- 相关：REQ-M3-004、REQ-M3-005、REQ-M3-007、REQ-M3-010；ADR-0003、ADR-0007；认证方案预留 ADR-0008

## 背景

任务书要求：某自习室存在维修中工单时，M1 下架该室全部座位；工单验收通过后恢复；M1 还必须记录状态来源。M3 和 M1 使用不同数据库，项目规则禁止跨库访问，也不允许未经 ADR 引入 MQ、分布式事务等基础设施。

普通同步 HTTP 无法覆盖“下游已经成功但响应丢失”或“M1 成功后 M3 在确认前重启”。如果 M3 直接回退状态，可能出现工单显示未维修但座位已下架；如果按教室恢复，可能误删另一张工单或 M2 的限制。

## 候选方案

### 方案 A：只做同步 HTTP 调用

M3 在请求内调用 M1，成功后更新本地状态，失败则返回错误。

- 优点：实现最简单，正常路径直观。
- 缺点：无法判断超时后的真实结果；重试可能重复下架，回退可能制造跨服务不一致；进程重启后没有恢复依据。

### 方案 B：本地持久化操作 + M1 幂等接口 + 定时恢复

M3 先在本地事务中保存中间状态和操作记录，再调用 M1。M1 按 `operationId` 幂等执行并保存结果，M3 可查询或重试；解除按 `restrictionId + source + sourceRef` 精确执行。

- 优点：不新增基础设施；能覆盖响应丢失和重启；每一步可追溯；可防止误删其他来源限制。
- 缺点：增加 `STARTING/RESTORING` 中间状态、操作表和恢复任务；系统会短暂最终一致，需要向用户展示处理中。

### 方案 C：引入 MQ 或分布式事务

通过消息队列传递下架/解除事件，或用分布式事务协调两库。

- 优点：成熟方案可支持较复杂的异步链路。
- 缺点：增加课程项目当前没有的基础设施、部署和运维成本；仍要处理幂等、重复消息和业务补偿；违反“无 ADR 不引入基础设施”的现有约束，收益不足。

候选方案及故障场景由 AI 协助整理；最终是否接受方案 B 仍由 M1/M3 人员评审。

## 决定

选择**方案 B**。

1. 开始维修时，M3 在本地事务中把 `ASSIGNED` 转为 `STARTING`，同时写 ACTIVATE 操作和动作记录；提交后调用 M1。M1 明确成功才进入 `IN_PROGRESS`。
2. 验收通过时，M3 把 `PENDING_ACCEPTANCE` 转为 `RESTORING`，同时写 RELEASE 操作；M1 明确解除成功才进入 `COMPLETED`。
3. 超时、断连、5xx 和响应无法解析都视为结果未知，保留中间状态，由恢复任务使用原 `operationId` 查询并重试。
4. M1 为限制保存 `source=M3`、`sourceRef=workOrderId` 和唯一 `restrictionId`。解除必须精确匹配这些标识，禁止按 `roomId` 清空限制。
5. M1 为操作保存结果。同一 `operationId` 同内容重放返回原结果，同键不同内容返回 409；已经解除的限制不能被旧 ACTIVATE 重放重新激活。
6. M1 的最小契约为：创建/确认限制、精确解除、按操作 ID 查询结果，路径和 DTO 见 `docs/specs/m3-repair.md` 第 7 节。
7. 维修限制一旦生效立即阻止新预约；已有预约由 M1 保留记录并标记为维修影响，不计学生违约。通知失败不撤销限制。

## 依据

最关键因素是不能把网络超时解释成业务失败。方案 B 在现有 MySQL、HTTP 和 Spring 定时能力内解决结果未知问题，也符合每个服务只访问自己数据库的边界。工单级限制标识使“同室多张 M3 工单”和“M2 占用叠加”都能独立解除和追溯。

## 代价与后续

- API 可能返回 202，前端必须展示“正在下架/正在恢复”，不能把中间状态显示为失败或完成。
- M3 需要操作表、恢复任务、退避、原子领取和人工处理状态；M1 需要保存幂等操作历史和限制生命周期。
- 最终一致期间，M3 与 M1 的展示可能短暂不同；以 M1 的限制事实决定是否接受新预约，以 M3 的工单事实决定维修流程。
- 运行久后需要定义操作记录和审计记录的保留期限；在课程首版中不物理清理，以保证演示和追溯。
- 若后续跨服务写回显著增多、HTTP 恢复任务难以维护，再另立 ADR 评估事务性消息/outbox 与 MQ；本决定不预先引入它们。
- D 的认证、服务身份、通知和审计仍由单独决策完成。本 ADR 不允许 M3 临时相信客户端自报身份。

## 如何达成一致

本稿由 M3 依据任务书、现有项目红线和当前 M1/D 能力起草。以下事项须在合并前由人确认并在本节记录：

1. M1 负责人确认三个内部接口、幂等语义和已有预约状态；
2. D/项目负责人确认物业管理员、物业主管等角色与通知接收规则；
3. M3 负责人确认中间状态和人工处理流程；
4. 有分歧时保留候选方案、评审意见和最终结论，不用 AI 自动解决跨模块冲突。
