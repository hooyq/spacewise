# ADR-0001：采用单仓库 + 主干开发、tag 发布

- 状态：提议中（待组内确认）
- 日期：2026-10-20
- 决策人：（待填）
- 相关：任务书“版本管理”“交付流水线”两节

## 背景

项目组约 6 人，分为至少 3 个模块组，系统包含 M1/M2/M3/D 共 4 个服务和一个前端。
任务书要求：变更经 PR 评审后合并；跨模块、公共层、schema 变更须经组内评审；
测试不过不能合并；部署版本有 tag 且能追溯到提交；生产发布需人工审批、可回滚。

需要决定两件事：代码放在几个仓库里，以及用什么分支策略。

## 候选方案

### 仓库组织

**方案 A：单仓库（monorepo）**，所有服务、前端、部署配置在一个仓库。
- 优点：只维护一套 CI 与规则文件；跨模块改动（如 M3 调用 M1 的新接口）在一个 PR 内完成并评审；
  从空环境一键部署整个系统更简单；AI 助手能同时看到调用方和被调用方。
- 缺点：所有人共用一条流水线，一个模块的测试失败会阻塞其他人合并；模块边界靠约定而非物理隔离。

**方案 B：多仓库（每个服务一个仓库）**
- 优点：更贴近真实的微服务组织方式；权限与发布天然隔离。
- 缺点：4～6 个仓库各需一套 CI、规则文件、分支保护；跨模块改动要多个 PR 协同合并；
  集成测试与整体部署需要额外编排；对 6 人课程团队维护成本过高。

### 分支策略

**方案 C：`dev` + `main` 双长期分支**：feature → `dev`（自动部署测试）→ PR → `main`（部署生产）。
- 缺点：两个长期分支需要持续同步，容易产生“dev 有、main 没有”的漂移和合并冲突。

**方案 D：主干开发 + tag 发布**：feature → PR → `main`（自动部署测试）；在 `main` 上打 `vX.Y.Z` tag → 人工审批 → 部署生产。
- 优点：只有一个长期分支；tag 直接标记部署版本，两个 tag 之间的提交就是本次发布内容；
  回滚 = 重新部署上一个 tag。
- 缺点：`main` 必须时刻可部署，对 CI 质量门禁要求更高。

## 决定

采用 **方案 A（单仓库）+ 方案 D（主干开发、tag 发布）**。

## 依据

- 课程考核的是过程质量而不是组织规模；单仓库把精力集中在一套 CI 与规则上。
- 跨模块写回（M2/M3 → M1）是核心集成点，单仓库下契约改动与调用方改动可同 PR 评审。
- 方案 D 让“部署版本 → tag → 提交”的追溯链天然成立，直接满足任务书的版本标记要求。

## 代价与后续

- 模块边界靠约定维护：用 `CODEOWNERS` 让改动自动请求对应模块组评审；`AGENTS.md` 红线禁止跨 schema 访问。
- 共用流水线的阻塞问题：后续 CI 按路径只构建受影响的服务（单独 ADR）。
- `main` 必须可部署：开启分支保护（必须 PR、必须 CI 通过、至少 1 人批准）。
