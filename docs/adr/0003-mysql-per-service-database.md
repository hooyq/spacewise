## 背景

需要为 4 个服务选择数据库，并落实“每个服务独立 schema、禁止跨 schema 访问”。
任务书要求版本化迁移、能从空库一次重放。组员数据库经验有限，学期内完成。
需要决定三件事：用哪种数据库；服务之间的数据隔离怎么做；自动化测试连什么数据库。

## 候选方案

### 一、数据库

**方案 A：MySQL 8.4 LTS**
- 优点：组员普遍更熟悉（数据库课程、以往项目用过）；中文资料多；8.4 是长期支持版。
- 缺点：DDL 不支持事务，迁移脚本执行到一半失败时会留下半成品，需要手动清理。

**方案 B：PostgreSQL**
- 优点：DDL 支持事务，迁移失败会整体回滚；SQL 标准支持更完整。
- 缺点：组员不熟，学习和排错成本更高。

**方案 C：MySQL 9.x（创新版）**
- 缺点：大约每季度发布一次，支持周期短，不适合需要稳定一学期的项目。

### 二、服务间数据隔离

**方案 D：一个实例、每服务一个库、每库一个专属账号**（账号只对自己的库有权限）
- 优点：越界访问会被数据库直接拒绝，把红线 2 从约定变成机制；只运行一个 MySQL 容器，资源占用小。
- 缺点：实例是共享的单点，一个服务的慢查询可能影响其他服务。

**方案 E：一个实例、每服务一个库、共用一个账号**
- 缺点：隔离只靠自觉，AI 生成的代码很容易顺手跨库查询。

**方案 F：每个服务一个 MySQL 实例**
- 优点：隔离最彻底。
- 缺点：4 个数据库容器，内存占用大，部署和备份都更复杂。

### 三、测试数据库

**方案 G：Testcontainers**，测试时自动启动真实的 MySQL 容器，用完即销毁。
- 优点：测的就是生产用的数据库；每次从空库重放全部迁移，直接验证“能从空库一次重放”。
- 缺点：跑测试需要 Docker；首次需要拉取镜像，比内存库慢。

**方案 H：H2 内存库（MySQL 兼容模式）**
- 优点：快，不需要 Docker。
- 缺点：只是模仿 MySQL，语法和行为有差异，可能测试通过而真库报错。

## 决定

**A + D + G**：MySQL 8.4；一个实例，每个服务一个库（`seat_db`、`room_db`、`repair_db`、`platform_db`）
和同名专属账号；自动化测试使用 Testcontainers。迁移由各服务自带的 Flyway 在启动时执行。

## 依据

- 选 MySQL 的关键因素是**组员熟悉**，能把有限时间留给流程和业务。
- 专属账号让“禁止跨库访问”由数据库强制执行，而不是只写在文档里。
- 测试必须对着真实的数据库跑，否则“测试通过”说明不了问题。

## 代价与后续

- MySQL 的 DDL 不在事务内：迁移脚本保持小而单一（一个脚本只做一件事），失败时先修复数据库再重新执行。
- 共享实例：资源问题出现时再考虑拆分实例。
- 测试依赖 Docker：在 README 和 CI 中写明。
- 建库、建账号脚本只在数据卷为空时执行；新增服务需要补充脚本并重建卷，或手动执行一次。
