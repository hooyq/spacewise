# ADR-0006：统一错误响应采用 ProblemDetail，由公共模块 web-common 实现

## 背景

在此之前，seat 出错时返回 Spring Boot 默认的错误格式（`timestamp/error/path`），网关返回 `ProblemDetail`，已经有两种格式。
业务开发开始后，4 个组还会各自再定义一套。前端和服务间调用都需要用同一种方式判断“成功还是失败、失败的原因是什么”。
需要决定三件事：成功的响应要不要包一层；异常处理的代码放在哪里；错误码用什么格式。

## 候选方案

### 一、响应格式

**方案 A：成功时直接返回数据，用 HTTP 状态码表示成败；失败时返回 ProblemDetail（RFC 9457），并扩展 `code`、`traceId` 字段**
- 优点：HTTP 标准做法，Spring 原生支持（网关已经在用）；网关访问日志和监控可以直接按状态码统计失败；
  服务间调用时 `RestClient` 遇到 4xx/5xx 会自动抛出异常。
- 缺点：部分组员和前端更习惯国内常见的 `Result` 包装写法。

**方案 B：所有响应统一包成 `Result<T>`（`code/message/data`），HTTP 状态码通常固定为 200**
- 优点：国内项目和中文教程中常见，组员熟悉。
- 缺点：失败时 HTTP 状态码也是 200，网关日志和监控看不出失败；服务间调用必须先解析 `code` 才能判断成败；
  与网关的 502/504 状态码语义冲突。

### 二、代码放在哪

**方案 C：公共模块 `libs/web-common`，所有服务依赖它**
- 优点：格式由同一份代码保证一致；通过 Spring Boot 自动配置生效，服务不需要任何配置。
- 缺点：改动会影响所有服务；服务之间多了一份共同的代码依赖。

**方案 D：每个服务各复制一份（与测试辅助代码的做法相同）**
- 缺点：统一格式的目的是“完全一致”，复制之后各组改着改着就又不一致了。

### 三、错误码

**方案 E：带模块前缀的字符串，如 `SEAT.ROOM_NOT_FOUND`**：可读性好；各服务用自己的枚举定义，不需要集中登记，靠前缀避免重名。

**方案 F：数字，如 `40401`**：需要查表才知道含义；各组之间要分配号段。

<!-- 候选方案由 AI 提出，人接受推荐（A + C + E）。 -->

## 决定

**A + C + E**。业务代码只需要 `throw new BusinessException(错误码, 说明)`。
未预料的异常一律返回 500 和固定文案“服务器内部错误”，**不返回异常信息**，完整堆栈只写日志。

## 依据

- 状态码有意义，这一点对网关、日志和服务间调用都很关键（A）。
- 统一格式的价值在于“一致”，必须由一份代码保证（C）。

## 代价与后续

- `libs/` 已加入 CODEOWNERS，改动须组内评审；只放框架代码，不放业务代码。
- 服务自己写 `@RestControllerAdvice` 时，必须设置高于全局处理器的优先级，否则会被全局处理器的兜底处理抢走（网关的 `DownstreamErrorHandler` 就是这样做的）。
- 错误码是接口契约，发布后不要改名。
- 调用方暂时只按状态码处理下游错误，解析下游的 `code` 等到真实业务需要时再做。
