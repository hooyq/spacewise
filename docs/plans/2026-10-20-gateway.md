# 计划：API 网关（搭建路线第 7 步）

- 日期：2026-10-20
- 关联：修订后的搭建路线第 7 步；ADR-0005（网关选型）；AGENTS.md 红线 5
- 状态：已确认（Spring Cloud Gateway Server WebMVC），已实现，待 PR 评审

## 目标

新增 `gateway` 作为浏览器访问后端的唯一入口（端口 8080）：
按路径前缀把 `/api/<模块>/**` 转发给对应服务；`/internal/**` 和各服务的 `/actuator/**` 一律不对外。
**不包含认证**：登录、权限校验等 D 组定下 RBAC 方案后，在网关上加过滤器即可。

## 范围

做：
- `services/gateway`：Spring Cloud Gateway（Server WebMVC 版），根 pom 引入 Spring Cloud BOM `2025.0.3`（对应 Spring Boot 3.5）。
- 路由（写在配置文件里，下游地址来自环境变量）：

  | 前缀 | 目标 | 默认地址 |
  |---|---|---|
  | `/api/seat/**` | seat-service | `http://localhost:8081` |
  | `/api/room/**` | room-service | `http://localhost:8082` |
  | `/api/repair/**` | repair-service | `http://localhost:8083` |
  | `/api/platform/**` | platform-service | `http://localhost:8084` |

  路径原样转发、不改写（第 6 步约定，服务自己的路径就带 `/api/<模块>` 前缀）。没有匹配上的路径一律 404，因此 `/internal/**` 自然不可达。
- 网关自己的 `/actuator/health`。网关不连数据库，所以它的健康状态不依赖任何下游服务。
- `deploy/compose.yaml` 新增 gateway（8080），用 `SEAT_SERVICE_URL` 等环境变量指向容器内的服务名。
- ADR-0005、AGENTS.md（网关、端口、“新接口必须带模块前缀，否则网关转发不到”）。

不做：
- 认证与权限（等 D 组的方案）。
- 跨域（CORS）配置：前端和网关同源部署时不需要，第 9 步再定。
- 限流、熔断、重试。
- 在 Compose 中关闭各服务的宿主机端口：本地调试仍要直接访问服务；生产环境的 compose 在第 8 步再收紧。

## 需要确认的取舍（写入 ADR-0005）

1. **网关用什么？**
   - A. **Spring Cloud Gateway（推荐）**：和服务同一套 Java 技术栈；以后认证（校验 JWT、传递用户身份）可以用 Java 写在网关一处，组员看得懂、能测试。代价是引入 Spring Cloud，多一个 BOM 要管理。
   - B. **只用 Nginx**：轻量，前端静态文件本来也需要它托管；但路由写在 Nginx 配置里，认证要么交给每个服务各做一遍，要么用 Nginx 的 `auth_request` 去调 platform-service，组员不熟，也不好测试。
   - 选 A 以后，第 9 步的 Nginx 只负责托管前端静态文件，并把 `/api` 转给网关。
2. **用 Spring Cloud Gateway 的哪个版本？**
   - **Server WebMVC（推荐）**：和我们的服务一样基于 Spring MVC，过滤器是普通的同步代码。
   - Server WebFlux：资料更多，但需要用响应式编程（`Mono`/`Flux`），组员要多学一套编程模型。课程项目的流量用不上它的性能优势。

## 测试

`RoutingTest`（`@SpringBootTest`，随机端口）：用 JDK `HttpServer` 启动一个假的下游服务，通过 `@DynamicPropertySource` 把 seat 的地址指向它。
网关不连数据库，没有 MySQL 容器的顾虑。

| 用例 | 断言 |
|---|---|
| `GET /api/seat/rooms?x=1` | 假下游收到的路径和查询参数是 `/api/seat/rooms?x=1`，响应原样返回给调用方 |
| `GET /internal/ping` | 网关返回 404，假下游没有收到请求 |
| `GET /api/unknown/x` | 404 |
| `GET /actuator/health` | 网关自身 UP |

## 验收标准

1. `mvn verify` 和 CI 通过。
2. Compose 下：`curl localhost:8080/api/seat/rooms` 和直接访问 8081 的结果相同；`curl localhost:8080/internal/ping` 返回 404。
3. `docker compose stop seat-service` 后，`/api/seat/rooms` 经过网关返回 5xx（不会一直挂着），网关自身 health 仍为 UP。
4. **测试有效性**：把 seat 路由的前缀改成 `/api/seats/**`，转发测试失败；加一条 `/internal/**` 路由，“不可达”测试失败。

## 风险

- Spring Cloud 和 Spring Boot 的版本必须配套。升级 Spring Boot 时要同步升级 Spring Cloud BOM，这一点写进 ADR-0005。
- 新接口如果忘了带 `/api/<模块>` 前缀，经网关会访问不到。在 AGENTS.md 中写明。

## 实现偏差记录

- 验收结果：
  - gateway 模块共 6 个测试通过。网关不连数据库，测试约 20s。
  - Compose 下：经网关访问 `/api/seat/rooms` 与直接访问 8081 的响应完全一致（md5 相同）；
    `/internal/ping`、`/internal/connectivity`、`/api/seat/../../internal/ping` 都返回 404。
  - 故意破坏：前缀改成 `/api/seats/**`、新增 `/internal/**` 路由，对应的测试都会失败。
- **验收 3 发现的 bug 及修复**：停掉 seat 后，经网关的请求**挂起约 80 秒**才返回 500。
  原因是网关转发时没有设置超时；而 500 也让人误以为是网关自身出错。
  按 AGENTS.md 的要求先写失败的测试 `DownstreamFailureTest`（期望连不上 502、超时 504，实际都是 500），然后修复：
  - `spring.http.client.connect-timeout: 2s`、`read-timeout: 10s`；
  - `DownstreamErrorHandler` 把 `ResourceAccessException` 转换成 502 或 504（`ProblemDetail` 格式）。
  修复后，Compose 中 seat 停掉时约 8 秒返回 502。比连接超时的 2 秒长，推测是 Docker 内置 DNS 解析已停止容器的服务名时有等待；
  这部分不受连接超时控制，暂不处理。
- 写测试时踩到的坑：`spring.http.client.read-timeout` 不仅作用于网关的转发，也会作用于测试里的 `TestRestTemplate`，
  导致测试客户端自己先超时。所以这个测试改用 JDK `HttpClient` 发请求。
- 偏差：
  - 计划外新增了超时配置和 502/504 映射（见上）。
  - compose 中把 healthcheck 抽成独立锚点 `x-healthcheck`，供网关和各后端服务共用（网关不需要 `depends_on: mysql`）。
  - 顺带在 AGENTS.md 中写入“本地只测改动的模块，全量交给 CI”（用户决定）。
