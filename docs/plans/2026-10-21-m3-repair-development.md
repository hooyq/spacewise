## 1. 目标与范围

交付可演示的闭环：选择空间并上报故障 → 物业管理员派单 → 维修人员开始维修 → M1 下架该室全部座位 → 提交完工 → 验收通过 → 撤销本工单对应的维修限制 → 报修人评价；同时支持超时工单升级和过程追溯。

已确定的边界：

- M3 位于 services/repair-service，端口 8083，仅使用 repair_db；浏览器通过网关 /api/repair/** 访问。
- D 负责身份与权限、空间主数据、通知、操作审计；M3 保留工单业务记录，不另建一套身份或空间管理系统。
- M3 通过 HTTP 调用 M1 的内部接口，下架来源必须标记为 M3，并关联具体工单。不得直接读写 seat_db，也不引用 M1 的实体或 Mapper。
- 已有 SeatClient、HttpClients、ServiceEndpoints、ServiceClientConfig 和连通性测试可以扩展；当前 ping 示例不代表维修业务链路已经完成。
- 任务书要求“验收通过后恢复”，因此提交完工并不立即恢复座位；同室还有其他限制时，只解除本工单的限制，是否可预约由 M1 重新计算。

首版包含任务书明确要求的全部 M3 能力。图片附件、库存与材料费用、外包结算、自动智能派单、复杂统计暂不纳入首版。取消工单作为建议扩展，先确认规则；自然语言业务代理是项目附加项，不替代基础功能。

前端方案尚未确定，先完成接口和可验证的后端闭环；团队确认前端技术栈后再实现报修页、我的工单、派单工作台、维修工作台与验收评价页。

## 3. 建议需求与验收基线

以下编号为草稿，正式使用前检查与其他需求是否冲突。表中的补充规则按第 2 节确认后生效。

| 编号 | 功能 | 最低验收标准 |
|---|---|---|
| REQ-M3-001 | 故障上报 | 校验空间、故障分类和描述；记录可信报修人；同一提交幂等键重试只产生一张工单，同键不同内容被拒绝 |
| REQ-M3-002 | 工单查询 | 支持本人列表、授权处理列表、详情及进度；分页和状态筛选正确；无权限用户不能读取他人工单内容 |
| REQ-M3-003 | 派单与改派 | 有管辖权限的管理员指派有效维修人员；并发派单只生效一次；保存指派历史；不允许普通用户自报角色后派单 |
| REQ-M3-004 | 开始维修及下架 | 被指派人员发起开始维修；M1 确认本工单下架后进入稳定的维修中状态；该室全部座位不可新预约，来源可追溯到 M3 和工单 |
| REQ-M3-005 | 维修完工提交 | 仅维修中工单可提交完工说明并进入待验收；待验收期间座位仍保持维修限制 |
| REQ-M3-006 | 完工验收与恢复 | 有权限者验收；不通过填写理由并回到维修中；通过后解除本工单限制；其他工单或 M2 占用存在时不能错误恢复可预约 |
| REQ-M3-007 | 评价 | 报修人可在工单完成后评价；评分范围、是否允许修改由需求确认；重复提交不产生多条评价，不能评价他人工单 |
| REQ-M3-008 | 超时升级 | 按已确认阶段和期限识别超时；记录升级级别、时间与接收人并通知；同一阶段周期的同一级升级不重复，重启后仍能处理 |
| REQ-M3-009 | 跨模块故障恢复 | 下架/解除响应丢失时保持处理中；同一操作重试幂等，进程重启后可恢复；不能误报恢复完成 |
| REQ-M3-010 | 通知、审计与隐私 | 上报、派单、维修、验收、升级等动作可追溯；通知失败可补发；日志不记录联系方式、报修正文或其他个人信息 |
| REQ-M3-011 | 取消未开始维修的工单（建议扩展） | 本人或授权管理员按确认规则取消；与开始维修并发时只一个动作生效；不得影响其他工单；已开始维修不能直接取消以绕过验收 |

跨模块验收单独写入 REQ-X 系列，至少覆盖 M3 下架、验收恢复、多工单来源隔离、M2 占用叠加和结果未知时的恢复。需求条目关联实现 PR、测试类或人工验收记录；未完成项保留状态和原因。

## 4. 领域模型及状态机

建议工单状态：

- SUBMITTED：已上报，等待派单。
- ASSIGNED：已指派，尚未开始维修。
- STARTING：已受理开始维修，等待 M1 确认下架。
- IN_PROGRESS：M1 限制已确认，维修中。
- PENDING_ACCEPTANCE：已提交完工，等待验收，维修限制仍然生效。
- RESTORING：已记录验收通过，等待 M1 确认解除本工单限制。
- COMPLETED：验收通过且本工单限制已解除。
- CANCELLED：未开始维修时按确认规则取消，终态（若采纳扩展需求）。

允许转换：SUBMITTED → ASSIGNED → STARTING → IN_PROGRESS → PENDING_ACCEPTANCE；验收不通过 PENDING_ACCEPTANCE → IN_PROGRESS；验收通过 PENDING_ACCEPTANCE → RESTORING → COMPLETED。取消仅允许从 SUBMITTED/ASSIGNED 进入 CANCELLED；改派只更新 ASSIGNED 的指派信息并追加记录。

M1 明确拒绝且确认本操作未创建限制时，STARTING 可退回 ASSIGNED 并记录原因；超时、断连、5xx 属于结果未知，不能直接退回。RESTORING 期间不得评价或重复验收，恢复任务继续确认解除结果。

超时升级使用独立的 escalation_level、due_at 和升级记录，不增加一个覆盖业务阶段的“超时”状态。返修重新进入维修阶段时生成新的阶段周期标识，期限是否重算由需求确定，历史升级不可覆盖。

建议表（仅位于 repair_db）：

1. repair_work_order：工单 ID、room_id、reporter_id、故障分类、描述、状态、assignee_id、version、阶段周期、阶段起始时间、期限、升级级别、提交幂等键和请求摘要、创建/更新时间。唯一约束 (reporter_id, idempotency_key)。
2. repair_work_order_action：追加保存派单、改派、开始维修、完工、验收、取消等动作，含操作者 ID、前后状态、时间、原因及操作标识；验收结果与完工说明需可追溯。
3. repair_work_order_operation：持久化 M1 下架/解除操作，含唯一 operation_id、work_order_id、restriction_id、动作、状态、尝试次数、下次重试时间及脱敏错误码。
4. repair_escalation：工单 ID、阶段周期、升级级别、接收人和发生时间；以 (work_order_id, stage_cycle_id, level) 唯一约束防止重复升级。
5. repair_evaluation：工单 ID、评价人 ID、评分、评价内容及时间；首版建议每工单一条评价，修改规则单独确认。
6. repair_delivery：如 D 的投递协议需要，保存通知/审计待投递内容、唯一事件 ID 和投递状态，与业务变更在同一本地事务内登记。

索引覆盖本人列表、维修人员待办、空间与状态查询、到期扫描、操作恢复。业务时间采用 Asia/Shanghai，API 时区及数据库时间存储约定写入 spec。D 空间只保留引用与必要历史快照，不重复维护主数据。测试与演示数据使用虚构身份，种子数据独立、脚本化且幂等。

## 5. 并发与跨模块一致性设计

建议采用“本地持久化操作 + HTTP 幂等下架/解除 + 定时恢复”，利用现有 MySQL 和 Spring 定时能力，不引入 MQ、Redis 等新组件。需要新增 ADR 比较纯同步调用与持久化恢复的复杂度；该方案是待评审建议，不能把 @Transactional 当成跨服务事务。

开始维修流程：

1. 本地短事务校验身份、指派关系和状态，条件更新 ASSIGNED → STARTING，同时写入下架操作和动作记录。
2. 提交本地事务后调用 M1，关联 source=M3、workOrderId、roomId、operationId，创建该工单的整室维修限制。
3. M1 在自身事务中建立限制，并使所有新增个人预约与整教室占用遵守同一并发互斥规则。下架不能仅靠前端隐藏列表，写入预约时也要检查。
4. 明确成功后，M3 保存 restrictionId，进入 IN_PROGRESS；明确拒绝且无副作用时退回 ASSIGNED；结果未知保持 STARTING，通过原 operationId 查询/重试。

验收通过流程：

1. 在本地事务记录验收人及通过结论，PENDING_ACCEPTANCE → RESTORING，并生成解除操作。
2. 通过准确的 source=M3 + workOrderId/restrictionId 请求 M1 解除限制，不能按 roomId 清空所有占用或直接设置“可预约”。
3. M1 确认解除后，M3 才进入 COMPLETED；仍存在其他维修工单、M2 时段占用或 M1 预约时，保留对应限制。对外展示“本工单处理完成”，不保证整个教室所有时段均可预约。
4. 解除结果未知时持续恢复；超过重试阈值进入人工处理队列，保留处理中事实及可追溯原因。

M1 契约至少提供限制创建、准确解除、操作结果查询三种能力。相同操作重放返回一致结果，同键不同内容拒绝；已解除后重放旧下架操作不能重新激活限制。M1 必须保存足够的操作结果/解除标记实现这个约束。

所有状态变化使用条件更新或乐观锁，派单、取消、开始维修、验收不能互相覆盖。恢复任务需要原子领取/租约或等效机制，允许多个实例扫描但不能并发重复推进同一操作；数据库版本和幂等协议仍是最终保障。

超时扫描与人工处理也必须并发安全：基于当前状态、阶段周期和期限条件登记唯一升级记录；通知引用升级事件，重试不重复创建升级事实。工单已经进入下一阶段时，旧阶段扫描不能继续升级。通知失败不撤销已经确认的维修、验收或升级事实。

## 6. 建议接口（尚不存在）

| 方法与路径 | 用途 |
|---|---|
| GET /api/repair/rooms | 获取有权限报修的空间，数据来自 D |
| POST /api/repair/work-orders | 创建报修工单，携带 Idempotency-Key |
| GET /api/repair/work-orders/mine | 查询本人上报的工单，支持分页与筛选 |
| GET /api/repair/work-orders/{id} | 查询授权范围内的详情、时间线与同步状态 |
| GET /api/repair/work-orders | 管理员/维修人员按权限查询待办，服务端强制限制范围 |
| POST /api/repair/work-orders/{id}/assign | 派单或未开工时改派，记录原因 |
| POST /api/repair/work-orders/{id}/start | 开始维修并申请下架；处理中返回 202 |
| POST /api/repair/work-orders/{id}/finish | 提交完工说明，进入待验收 |
| POST /api/repair/work-orders/{id}/acceptance | 提交验收通过/不通过及理由；待解除限制时返回 202 |
| POST /api/repair/work-orders/{id}/evaluation | 完成后的评价 |
| POST /api/repair/work-orders/{id}/cancel | 按确认规则取消未开工工单（建议扩展） |

超时升级首版由后台任务触发，不提供任何用户都能调用的升级接口；人工重试/升级若需要管理接口，必须单独定义权限、审计和验收标准。

M1 内部接口路径放 /internal/**，名称和 DTO 由 M1/M3 共同确认。D 提供空间、可信身份、角色与管辖范围、通知及审计契约；不能依赖前端传入 reporterId 或角色声明判断权限。

成功返回 DTO，不套 Result；错误使用 ProblemDetail + code + traceId。建议稳定错误码 REPAIR.WORK_ORDER_NOT_FOUND、REPAIR.INVALID_STATE、REPAIR.FORBIDDEN、REPAIR.INVALID_ASSIGNEE、REPAIR.IDEMPOTENCY_CONFLICT；参数格式校验沿用 COMMON.VALIDATION_FAILED。HTTP 400/401/403/404/409/503 和资源存在性隐藏策略在 spec 中与 D 对齐。

## 7. 两人分工

参照 M2 暂按两人纵向拆分。用户已认领 M3，第二位成员及 A/B 对应人员尚未确定，不在文档中虚构姓名；若最终由一人承担，保留工作包但顺序实施，并重新估算工期。

| 工作 | 同学 A：报修与验收侧负责人 | 同学 B：派单、维修与联动侧负责人 |
|---|---|---|
| 共同设计 | 需求、状态机、DTO、数据表、超时规则、权限及 M1/D 契约 | 同左，互审后确认首版 |
| 后端主责 | 空间查询、报修提交、本人列表/详情、未开工取消、验收申请、评价 | 派单/改派、维修待办、开始维修、完工提交、M1 客户端及持久化恢复 |
| 状态协调 | 验收与取消调用统一状态服务；验收通过只登记解除意图，不自行宣称座位已恢复 | 维护统一状态转换和 M1 操作执行；确认解除后完成工单 |
| 超时升级 | 负责阶段期限计算、定时扫描、升级记录与幂等测试 | 提供阶段转换及阶段周期数据，协助扫描与人工操作并发验证 |
| 通知/审计 | D 客户端与投递适配、待投递任务恢复、查询展示 | 各业务动作事务中登记动作及待投递事件，共同核对隐私边界 |
| 前端（选型后） | 报修表单、我的工单、详情、验收及评价页面 | 派单工作台、维修工作台、处理中与失败待处理展示 |
| 测试 | 参数校验、本人权限、提交幂等、验收评价、超时升级及投递 | 状态机、派单竞态、M1 下架解除幂等、多工单隔离、超时与重启恢复 |
| 文档与交付 | 报修/验收使用说明、需求追踪、伦理问题记录 | M1 联调记录、故障恢复说明、演示步骤与测试证据 |

B 的一致性任务较重，A 完成报修侧后优先协助多工单、超时恢复与通知测试。共享实体、状态枚举、DTO 与迁移先在基础 PR 中确定；涉及验收、恢复和升级的共同文件指定主修改人，另一人评审，不能各写一套状态更新逻辑。

M1 的限制存储及预约检查由 M1 组负责，D 的公共能力由对应负责人实现；本表分配的是 M3 的调用、需求协调和联合验收职责，不把其他模块的开发工作默认为 M3 已承接。

## 9. 实施阶段与 PR 切分

以下暂按两人兼职约 9–12 个有效工作日估算，并非承诺日期；取决于 M1/D 接口、前端选型及双方实际投入。阶段退出条件优先于天数。

| 阶段 | 工作量建议 | 交付与退出条件 |
|---|---|---|
| P0 需求与契约 | 1–2 天，两人 | 需求、权限、验收主体、超时规则、状态机、M1/D 接口及恢复 ADR 完成评审；A/B 人员落实 |

| P3 完整联动 | 2–3 天，两人 | 真实 M1/D 联调，下架、验收恢复、多工单隔离、权限、超时升级和崩溃恢复通过 |
| P4 页面与交付 | 2 天，两人 | 按已确定前端方案接页面；集成环境演示、需求追踪、测试与伦理证据齐备；选型延迟则重估 |

建议 PR：①需求/设计/分工与 ADR；②迁移及共享模型；③报修查询提交；④派单、维修开始与 M1 下架；⑤完工、验收与解除恢复；⑥超时升级、通知审计与评价（过大则再拆）；⑦页面及联合验收。

## 10. 测试与验收

- 报修与权限：非法空间/空描述被拒绝；A 不能查询、取消或评价 B 的私人工单；普通用户不能派单；非指派人员不能开始维修；验收权限和禁止自验按最终规则生效。
- 状态机：不能未派单就维修、未维修就完工、未验收就完成；验收不通过回到维修中且不解除限制；RESTORING 不允许评价；并发派单、取消与开始、重复验收只允许合法转换。
- 超时升级：以可控制的 Clock 测试期限前、到期点、期限后；重复扫描、多个扫描器、服务重启和返修周期不重复/遗漏升级；已进入下一阶段的工单不被旧扫描升级。不要靠长时间 sleep 验证时限。
- 跨模块：同室两张维修工单分别建限制，仅验收一张时座位仍不可预约；最后一张验收后也不能清除已有 M2 占用；M1/M2 新预约与下架并发时遵守共同互斥协议。
- 故障恢复：M1 未收到请求、已下架但响应丢失、M1 成功后 M3 落库失败、解除响应丢失、恢复任务中途重启，均能通过原操作标识恢复；下游不可用不能令本服务 health 变 DOWN。
- 幂等与追溯：重复上报不生成重复工单；同键不同内容拒绝；下架/解除可重放；解除后旧请求不能复活限制；能展示 source=M3、workOrderId、operationId。
- 通知与隐私：D 不可用时投递保留待补发，恢复后不重复产生业务动作；通知与审计有幂等标识；错误响应及日志不泄露工单正文、联系方式或内部异常。
- 测试有效性：在临时工作区分别故意移除权限校验、放宽非法状态、让验收前解除限制、取消升级去重，确认对应测试失败；恢复实现后重新通过，记录命令、结果和关联提交，不合并破坏代码。
- 集成测试使用现有 @IntegrationTest 与真实 MySQL Testcontainers，验证迁移和实际 HTTP 行为；客户端可使用本地 HTTP 假服务模拟超时/错误，不 mock 被测业务逻辑本身。
- 本地执行：mvn verify -pl services/repair-service -am；迁移检查 bash scripts/ci/check-migrations.sh；全量构建交 CI。与其他组约定联调/部署窗口，避免测试期间环境正在更新。
- 演示：上报 → 派单 → 开始维修 → M1 全室座位下架 → 完工待验收仍下架 → 验收通过 → 本工单限制解除 → 评价；另演示一次超时升级、多工单隔离及网络失败后的恢复。需通过真实网络调用展示状态写回，不能只展示 ping 或截图。

本文件仅为计划与分工草稿，未新增业务实现，未运行业务构建或测试，以上验收结果均待实施后填写。

## 11. 风险与应对

1. M1/D 契约未就绪：P0 明确负责人、接口样例和最晚就绪节点；可先做契约替身测试，但真实集成是交付门槛。
2. 多工单与多来源恢复错误：以工单级限制标识解除，不写“room.available=true”式覆盖逻辑；把多工单、M2 叠加列入必测。
3. 超时升级仅停留在文档：从需求阶段确认计时规则与接收人，持久化阶段期限、唯一升级记录和待投递事件，提供可演示验证方式。
4. 分工负载不均与共享文件冲突：A 承担升级与投递，B 聚焦状态和 M1 恢复；基础模型先合并，后续按主责维护、互审；冲突交人处理。
5. 维修影响已有预约的公平性：下架可能影响已预约学生，必须和 M1/M2 确定通知、解释及补救方案；不能默默清除预约或把服务故障归为学生违约。
6. 验收与评价的利益冲突：明确维修者不能自行验收，保留验收理由和处理过程；评价不应直接等同于维修人员绩效，争议处理与内容访问范围需记录决定。
7. 隐私与责任：报修正文可能含个人信息，只按任务所需授权读取；日志不记正文，审计记身份 ID 与动作；保留期限、删除与追溯之间的取舍与 D 共同确认。
8. 前端和人员未定：本计划不指定未经确认的框架或第二位成员；确认后补文件级计划与工期。每位成员持续记录本人参与的真实取舍，供个人工程伦理论文使用。
